The Problem

Bridge data exists. It's trapped in PDFs.

German bridges are inspected under DIN 1076 every six years. Each inspection produces a Bauwerksbuch — a structured PDF of 20–30 pages containing physical attributes, full inspection history, individual damage records with photos, and maintenance history. The data is there. Nobody is turning it into decisions.

In December 2021, the Rahmedetalbrücke on the A45 collapsed and closed overnight. The structural decline was visible in the inspection history for years. Nobody connected it to an action in time. BrückenPilot exists to close that gap.

Where to find qualified bridge contractors?

The PQ-Verein (Präqualifizierungsverein) maintains the official German public construction registry. We downloaded multiple CSV exports filtered by bridge-relevant Leistungsbereiche (service categories) — prestressed concrete work, steel construction, corrosion protection, concrete rehabilitation, waterproofing, and full-service bridge construction.

These CSVs were combined into a single clean dataset: duplicates removed by PQ-Nummer, service categories merged per firm, and address fields normalized.

📍

Turning addresses into map coordinates

Every contractor needed GPS coordinates for proximity filtering. We used the OpenStreetMap Nominatim geocoder with a multi-level fallback strategy:

  • Full address — street + postal code + city (highest precision)
  • City-center fallback — postal code + city only (when the street wasn't found)
  • Rate-limited to 1 request/second, with exponential backoff on errors
  • Failures logged to a separate CSV for manual review

The result: a geocoded JSON of all qualified bridge contractors across Germany, upserted into the database once and reused for every bridge analysis.

The Core Engine

From PDF to structured intelligence in 8 steps

The batch pipeline processes each Bauwerksbuch PDF through a deterministic, auditable sequence. Every step is isolated — a failure in one PDF doesn't affect the rest. A SHA-256 hash ensures idempotent re-runs.

1  Text Extraction

The PDF's text layer is read with full page markers for source linking. If the average characters per page is below 50, the PDF is flagged as a scan — an image-only document with no selectable text. In that case, every page is OCR'd using Tesseract with the German language model. If OCR still yields nothing, the PDF is marked as failed and the batch moves on.

2  Photo Extraction

Section 7.4 (Schäden) is located in the document, and inspection photos are extracted from that range. Digital PDFs yield clean embedded image objects. Scanned PDFs are trickier — photos may be embedded among rasterized text strips (filtered by minimum pixel size), or stitched from vertical tile-pairs that need merging. When nothing is embedded, a layout detection model (DocLayout-YOLO) crops the figure regions directly.

3  Structured LLM Extraction

The full page-tagged text is sent to a large language model in a single call. The model returns a fully structured record: bridge identity, UTM coordinates, complete inspection history, every individual damage with its severity ratings and photo references, and all past maintenance work — all validated against a strict schema. Domain sanity gates reject nonsensical outputs (missing Bauwerksnummer, grades outside 1.0–4.0).

3b  Photo–Damage Matching

Each damage carries a photo reference ("Bild:") that also appears in the caption below its photo. This binding is deterministic — no LLM, no pixel heuristics. For digital PDFs, the caption is read from the text layer and matched by leading-token prefix. For scans, the caption is OCR'd and matched by IDF-weighted shared tokens, requiring a token unique to one caption — which keys on the discriminating ID number and ignores boilerplate. A damage with no confident match simply gets no photo (honest over guessing).

4  Coordinate Conversion

Bridge locations in the document are typically in UTM (ETRS89). These are converted to WGS84 (GPS coordinates) with the correct zone based on the document's reference system. When no UTM coordinates exist (older documents), the bridge address is geocoded as an approximate map pin — clearly marked as "geocoded" vs. "exact" in the data.

5  Priority Scoring

Every bridge receives a composite priority score (0–1) from three factors: Condition (current grade + severity boost), Criticality (road class, traffic volume, detour difficulty), and Deterioration Trend (linear regression on historical grades, with a material-age fallback for sparse data). The full breakdown is stored for transparency — every number is explainable.

6  Contractor Capability Matching

Based on the specific damages found, the system determines which PQ service categories are needed for repair. This capability set is stored on the bridge record and used by the frontend to filter qualified contractors — combined with distance calculated in the browser for real-time proximity filtering.

7  Intelligent Summary

A second LLM call generates a three-part assessment using the now-complete bridge record including matched photos: Situation (current state), Risks (what could deteriorate), and Recommendation (intervention type with cost range). This is the only generated prose — everything else is structured data.

8  Persist to Database

The original PDF, matched photos, and all structured data are uploaded to cloud storage and upserted into the database. The operation is fully idempotent — re-processing the same PDF overwrites cleanly without creating duplicates. Child records (inspections, damages, maintenance) are replaced atomically.

Engineering Challenges

Problems we solved along the way

Real-world PDFs don't cooperate. Every German state has a different template, documents span decades of formatting conventions, and scanned documents break every assumption about machine-readable text.

📄 Ingestion

Scanned vs. Digital PDFs

Digital PDFs have a text layer — read it directly. Scanned PDFs are images with no selectable text. The system auto-detects which type it's dealing with and switches to OCR. For photos, scans may embed images as stacked vertical tiles that need stitching, or as completely flat rasters requiring layout-model cropping.

📸 Matching

Photos Without Metadata

PDFs embed photos as raw image objects — no filename, no caption attached. The system reads the text directly below each photo's bounding box, clips it to the photo's column to avoid bleeding from adjacent layouts, and matches it against the "Bild:" reference the LLM extracted from the damage record. Two different algorithms handle digital and scanned documents.

🗺️ Coordinates

16 States, Multiple Coordinate Systems

Bridge documents use UTM coordinates with different reference systems (zone 32N or 33N depending on geography). The system reads the reference system from the document, selects the correct EPSG projection, and converts to GPS. When coordinates are missing entirely, address geocoding provides a usable fallback.

🧠 Extraction

One LLM Call per Document

The entire document text is processed in a single LLM call with strict schema enforcement. This avoids the cascading errors of multi-step extraction and ensures every field — from bridge dimensions to individual damage photo references — is extracted in context. Domain gates catch hallucinated or structurally invalid output before it reaches the database.

🏗️ Contractors

Historical vs. Available Firms

The PDF contains past contractors who worked on the bridge — but they may no longer exist. BrückenPilot separates these clearly: historical firms are shown as factual records, while the Contractors tab shows currently active, PQ-qualified firms matched by capability and proximity. Two completely different data sources, one clear interface.

🔄 Operations

Idempotent Everything

Every operation — from PDF upload to database upsert — is designed for safe re-runs. Storage paths are deterministic (derived from the Bauwerksnummer), database writes use upsert-on-natural-key, and the batch runner tracks SHA-256 hashes to skip already-processed files. A crashed overnight run simply resumes where it left off.

The Interface

From data to decisions

The frontend is a real-time monitoring dashboard that reads directly from the database. No backend server required — the browser talks to Supabase with row-level security.

🗺️ Interactive Map

Every bridge plotted on a choropleth map of Germany. States are tinted by their worst-urgency bridge. Markers pulse for critical condition. Click to inspect.

📊 Priority Dashboard

Condition grade, priority score with full factor breakdown, inspection history chart, estimated costs, and AI-generated risk assessment — all in one panel.

🔍 Damage Inspector

Every damage record with severity ratings (S/V/D), location description, and matched inspection photos with a full-screen lightbox viewer.

🏢 Contractor Finder

Active PQ-qualified firms filtered by distance slider and matched by the specific repair capabilities the bridge needs. All computed in the browser.

📄 Source PDF Access

One click opens the original Bauwerksbuch PDF. Every extracted value is traceable back to its source page — the ultimate audit trail.

🌗 Adaptive Theme

Full dark and light mode with a design system built on HSL CSS variables. Glassmorphism cards, gradient accents, and smooth micro-animations throughout.
